# B站搬史机（mai repost shit）

定时去B站捡**评论区全是艾特**的视频，下载成 720p，以「聊天记录」（合并转发）的形式搬进群。

## 它怎么判断一条视频是屎

**唯一判据：评论里含 `@` 的比例 ≥ 阈值**（默认 50%），且评论样本数达标（默认 ≥ 30 条）。
样本不足直接判「样本不足」而不是当命中——「两条评论里有一条带 @」是噪声，不是信号。

这条判据是实测出来的：鬼畜类候选 4/4 命中、艾特率中位 64%；对照组只有 3%~23%。

## 检索范围

| 项 | 默认 |
|---|---|
| 播放量 | 5万 ~ 30万 |
| 发布时间 | 3 ~ 30 天前 |
| 排序 | `totalrank` + `pubdate` 随机 |
| 分区 | **不限定**，用关键词池捞候选（鬼畜/抽象/整活/绷不住/答辩/逆天…） |

关键词池比阈值更决定成败：实测偏主流搞笑的词两轮 15 条候选 0 条过 50%，
换成泛鬼畜混合词后 10 条里过 2 条。池子可以在配置里随便改。

## 画质与体积

免登录的 `playurl` 最高就给到 **720P**，所以「压到 720p」= 选清晰度档位下载，
**不需要 ffmpeg**，也不需要 SESSDATA。

体积控制分两步：先按 `quality_preference` 试最高档，用接口返回的 `size` **在下载前**判断体积；
超限就**自动往下降一档**（720P → 480P → 360P），而不是丢掉这条候选。

> ⚠️ **别把 `max_size_mb` 调太大。** 实测一条 190 秒的视频被下成 35.4MB 后，
> 三种投递方式**全部**被平台判失败（NapCat 上传失败），而且群里还可能已经出现半条消息。
> 默认 15MB 是有原因的经验值：同一位置降到 360P 只有 11.2MB，就能正常发出去。

## 投递形式

一条合并转发，节点内容是「说明文字 + 视频本体」：

```
【视频标题】
UP：xxx　分区：xxx
播放 123,456　点赞 1,234　收藏 5,678
时长 1分10秒　评论区艾特率 64%（38/59）
https://www.bilibili.com/video/BVxxxxxxxxx
```

**只有这一种投递方式**：不会退回「直接发视频」或「按文件发」（那会在群里多出消息）。
投递失败时只在本地记 error 日志，**不往群里发任何提示**——群里只会看到搬出来的视频。

## 频率

一天 `daily_times` 次（默认 3 次），时刻在 `active_hours` 内随机分布，状态落盘，
重启不补发；错过计划时刻超过 `catch_up_minutes` 直接跳过。

## 安装与配置

1. 装到 MaiBot 的 `plugins/` 下（插件中心安装或手动放目录）。
2. 打开 `config.toml`，填 `[target].groups`（群号），把 `[plugin].enabled` 改成 `true`。
3. 保存即热重载，下一轮生效。

关键配置项：

```toml
[plugin]
enabled = false          # 装完默认关闭，不会自己发东西
config_version = "1.0.0"

[target]
groups = []              # 目标群号列表
daily_times = 3          # 每天搬几次
active_hours = [9, 23]   # 允许发送的时段

[source]
play_min = 50000
play_max = 300000
window_hours = [72, 720] # 发布时间窗（小时）
keywords = ["鬼畜", "抽象", "整活", "绷不住", "答辩", "逆天", "难绷", "离谱", "沙雕", "搞笑", "名场面", "迷惑行为", "吐槽", "社死", "破防", "神操作"]
min_video_review = 40    # 评论数下限，保证艾特率有分母
max_check_per_run = 12   # 每轮实际检查几条候选

[judge]
at_ratio_threshold = 0.5 # 艾特率阈值
min_comments = 30        # 评论样本下限

[filters]
title_blacklist = ["原神", "崩坏", "星穹铁道", "剧透", "直播回放", "录播", "合集"]

[tool]
enabled = true           # 允许群友用自然语言点播
cooldown_minutes = 10    # 同一个群的冷却
daily_limit_per_group = 3
max_count = 3            # 单次最多搬几条
```

完整模板见 [config.toml.example](config.toml.example)。

## 自然语言驱动（默认全员可用，可收紧）

除了命令，插件还注册了一个 LLM 工具 `repost_shi`，群友直接说话就能点播：

> 群友：来点抽象的 / 搬个史 / 有没有鬼畜的，整两个

模型会调用 `repost_shi`，可以带 `topic`（口味关键词，如「鬼畜」）和 `count`（1~3 条）。
工具**立即返回**，视频在后台下载完自动发到当前群，所以不会卡住对话。

**点播之后机器人不会在群里多说话**：插件会吞掉紧随其后的那一条回复
（走 `maisaka.reply.before_post_process` 钩子把回复文本置空，宿主对空回复的处理是不发送），
所以群里只会出现视频本身，不会出现「搬着呢」「刚给你下了几个」这类话。
只吞点播后的第一条，之后的正常聊天不受影响；不想要这个行为就把 `[tool].suppress_reply` 关掉。

> ⚠️ **权限边界，请先看清楚**
> **默认 `[tool].permission = "anyone"`——群里任何人都能用一句话触发搬运。**
> 命令 `/搬史`、`/搬史测试` 是管理员专属，但工具不是：宿主在群聊里给工具回调的
> `user_id` 恒为空，无法直接判断是谁在点播。
>
> 想收紧就设 `permission = "whitelist"` 并在 `whitelist` 里填 QQ 号。实现方式是注册
> 入站钩子 `chat.receive.after_process` 按会话缓存最近一位真人发言者，触发时回查
> （缓存有效期 `speaker_cache_ttl_seconds`）。缓存是「该会话最近发言者」而不是
> 「触发这次调用的人」，同一群多人抢话时可能错位，所以**白名单模式下认不出发言者就拒绝**，
> 宁可少搬也不放过。最严格的做法是 `[tool].enabled = false`，只留管理员命令。

点播**不限次数、没有冷却**——只留一个最小间隔护栏 `min_gap_seconds`（默认 60 秒），
挡住"刚搬完又来一条"的贴脸连点，单条点播最多搬 `max_count`（默认 3）条。

## 另一个频道：来点好看的（二次元向）

除了搬史，还能点播**二次元画向**的短视频：

> 群友：来点涩的 / 来点色的 / 来点黄的 / 来点好看的 / 来点好康的

**这句话是命令触发的，不经过模型**：说「来点好看的 / 来点涩的 / 来点色的 / 来点黄的 /
来点好康的」会直接命中插件的命令正则，机器人**不会回话**（消息被拦截，不进 LLM），
群里只会出现视频。搬史同理：「来点史 / 搬点屎 / 来点抽象的」。

> 为什么不用模型调用工具：实测在群里说「来点好康的」时，模型只是聊天式回绝
> （「好看的没有了」），根本不调用工具——所以这类固定说法走命令链才可靠。

对应工具 `repost_pretty`（模型主动调用时走这条），判据与搬史完全不同：

| 条件 | 默认值 | 说明 |
|---|---|---|
| 时长 | ≤ 120 秒 | 「时长不长」就是这个闸门 |
| 收藏率（**收藏/点赞**） | ≥ 0.50 | 实测 73 条候选：中位 0.516、≥50% 有 39 条、≥100%（收藏比点赞还多）有 13 条 |
| 分区 | `typename_whitelist` | 子分区白名单：MMD·3D / 同人·手书 / MAD·AMV / 人力VOCALOID / 动画综合 等 |
| 内容类型 | 关键词 + `block_words` 屏蔽 | 只要 MMD/3D 纸片人舞蹈、动漫剪辑（MAD/AMV）、手书/同人动画 三类 |

**只要二次元、不要真人**是靠子分区白名单实现的：搜索接口返回的 `typename` 是子分区，
二次元和真人内容落在完全不同的子分区里（真人向是 仿妆cos / 颜值·网红舞 / 舞蹈综合 / 特摄），
所以在 170 条采样里白名单筛完后没有一条真人出镜；另有 `real_blacklist` 词表兜底。

想收宅舞（真人出镜但属二次元文化）就把 `"宅舞"` 加进白名单；想更严就把
`min_favorite_rate` 调到 0.8 或 1.0。

> **为什么收藏率的分母是「点赞」而不是「播放」**：B站上收藏数远小于播放数，
> 收藏/播放到 50% 意味着"每两个播放就有一个收藏"，实测 73 条候选里最高只有 40.1%；
> 而"每两个点赞就有一个收藏"是常见的（中位 51.6%），收藏比点赞还多的也不少。
> 想换回播放当分母就把 `favorite_rate_metric` 设成 `fav_play`（阈值需相应调小）。这一步的冷却与每日额度与搬史**分开计**。

三类要什么：**MMD/3D 纸片人舞蹈、动漫剪辑（MAD/AMV）、手书/同人动画**——
画面或动态本身就是看点；静态图文/壁纸合集不在其中（分区白名单已去掉插画·绘画）。
虚拟主播（Hololive 等）的 MMD 内容保留，但直播切片/会限/杂谈排除。

另外这个频道会挡掉两类「不是好看的画面」的内容：

- **教程/讲解类**：`block_words` 默认含 教程/教学/教你/手把手/零基础/入门/画法/步骤/解析/
  讲解/思路分享/干货/保姆级；
- **低创自制剧集**：`block_words` 另含 新番/自制剧/连续剧/小剧场/剧情向/大电影/剧场版/解说/配音，
  并用一条正则挡剧集编号（`第 4 集`/`EP4`/`第二期`）。

数值指标抓不住「低创」（实测那条播放 3.6 万、点赞率 3.8%、收藏/点赞 1.89 全都正常），
所以靠上面两层规则 + 剧集编号正则来挡。**频道不调用 LLM**：判定完全由关键词、分区白名单、
屏蔽词和阈值决定，行为可预测、不随模型口味飘。

## 目标解析与"过期聊天流"的坑

配置里填的群号/QQ 号会被解析成宿主的聊天流。这里有个坑：**同一个群可能存在多条历史会话**，
宿主的 `chat.get_stream_by_group_id` 取的是第一个匹配，可能返回**过期的那条**——它的路由元数据是老的，
会落到 legacy 旧链、发送必然失败（现象就是"手动能发、定时发不出去"）。

所以插件的解析顺序是：

1. **入站消息学到的活动聊天流**（收到该群/该人消息时记下，落盘持久化）——最准；
2. 缓存为空时，枚举同目标的多条会话，用 `message.get_recent` 看**哪条最近有消息**；
3. 都拿不到才回退宿主的 `get_stream_by_group_id` / `get_stream_by_user_id`。

## 没找到会继续找

一轮没挑到符合条件的候选时，插件会**换关键词/翻页再找**，最多试 `[retry].rounds` 轮
（默认 3），两轮之间等 `gap_seconds` 秒（默认 15）。全都没找到才放弃并记日志
「找了 N 轮都没找到符合条件的候选」。定时轮与点播都走这套逻辑。

嫌请求多就把 `rounds` 设成 1（退回"一轮定生死"），或者只调大 `gap_seconds`。

## 投递方式与它的风险

投递成一条**聊天记录**（合并转发），里面是**两个节点**：第一个是说明文字，第二个只有视频。
视频默认**内联成 base64** 塞进消息（`inline_video_max_mb`，默认 10MB）——因为后端
（实测 SnowLuma）可能跑在另一个文件系统/容器里，给它本机路径会 `EACCES` 读不到；
超过上限才退回路径引用并打 warning。
分成两个节点是必须的——经 SnowLuma 适配器发送时，对端 QQ 会拒绝"文字 + 视频"同节点，
报 `message element "video" must be the only segment in a message`。需要知道的是：

- 宿主没有 VideoComponent，节点里的视频段靠「未知类型 → 适配器兜底识别」这条路走通，
  写法是 `{"type": "video", "file": "<本地路径>"}`。**这依赖宿主的内部实现，不在公开 API 里。**
  宿主一旦改动段归一化逻辑，这条链会**安静地**坏掉（只留下一条 warning）。
- **只有这一种投递方式**，不会退回「直接发视频」或「按文件发」——那会在群里多出消息。
- 失败时只在本地记 error 日志，**不往群里发任何提示**：群里只会看到搬出来的视频。
  排查看日志里的 `投递失败（合并转发未成功…）`，同时注意体积——体积过大时
  NapCat 会判失败且不给原因，可调小 `[download].max_size_mb`。

## 内容说明

**本插件只做一件事：把B站评论区艾特率超标的公开视频转发进群。它不做内容审核**——
判据只有「评论区 @ 比例」，命中的视频会直接进群，请自行确认是否符合你的群规与平台要求。

代码里**没有**内容安全词表、也不按分区拦内容；只保留用户自己配的屏蔽词
（都在 `[filters]`，都是子串匹配、命中即跳过）：

| 配置 | 作用 |
|---|---|
| `title_blacklist` | 标题屏蔽词，默认挡的是长剧集 / 直播切片 / 剧透这类容易混进来的内容 |
| `tag_blacklist` | 标签屏蔽词 |
| `up_blacklist` | UP 主屏蔽词 |

另外还有与内容无关的硬上限：`max_duration_seconds`（时长）、`max_size_mb`（体积）。

## 实现上的三条硬规则

改 `core/bili_api.py` 之前请先读这段：

1. **搜索接口必须带 `buvid3`**（先访问一次首页种 cookie），否则返回 `-412`。
2. **评论接口必须完全不带 cookie**：带上 `buvid3` 后每页只返回 3 条且 `is_end=True`。
   所以代码里开两个 httpx client，绝不混用。
3. **视频 CDN 校验 Referer**：必须带 `https://www.bilibili.com/`，否则 403。

投递侧还有两个约束：视频段必须写成 `{"type": "video", "file": "<本地路径>"}`（顶层 `file` 键），
且不能走 base64——插件与宿主之间的 RPC 帧上限 16MB，base64 还会膨胀 4/3。

更多实测数据（命中率、翻页深度对比、验收记录）见 [docs/NOTES.md](docs/NOTES.md)。
