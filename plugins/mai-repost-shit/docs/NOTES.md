# 实测数据与接口状态（NOTES）

本文件记录插件判据与接口的实测依据，供后续调参和排查用。数据采集于 2026-10-11。

## 一、艾特率判据的实测样本

每视频取最多 60 条评论（裸请求 3 页 × 20 条），统计含 `@` 的比例：

| 通道 / 分区 | 播放下限 | 有效样本 | 艾特率 |
|---|---|---|---|
| 鬼畜 tids=119 | 5 万 | 4/4 | 16.3% / 52.5% / **64.4%** / 66.1%（中位 64.4%） |
| 娱乐 tids=5 | 3 万 | 1/4 | 3.3% |
| 时尚 tids=155 | 3 万 | 1/2 | 23.3% |
| 搞笑 tids=138 | 1 万 | 1/4 | 0%~21.7%（多数视频评论不足 30 条） |

结论：判据成立且区分度强，但 **1万播放档的视频评论样本普遍不足**，
所以插件里把 `min_video_review` 前移到搜索阶段，并要求评论样本 ≥ `min_comments`。

## 二、「1万~10万 → 5万~30万播放」的检索配置实测

采样方式：4 个关键词 × 50 条，统计落在播放区间内的比例。

| 排序 | 时间窗 | 命中率 |
|---|---|---|
| `totalrank` | 72~336h | **18.0%** |
| `pubdate` | 36~168h | 6.0% |
| `pubdate` | 168~336h | 10.5% |
| `pubdate` | 336~720h | **23.0%** |
| `click` | 24~168h | **0%** |
| `click` | 72~336h | **0%** |

`click` 为 0 的原因：它只返回爆款（page1 就是 3000 万~1.3 亿播放），
且深翻页在 **~1400 万播放**处被截断（page=20 与 page=50 返回同一批），拿不到中间播放量。

加分区限定时命中率会更高（kw=搞笑 + tids=138 + 36~72h → 44~48%），
但本插件按要求不限定分区。

## 三、接口可用性

**免登录可用**

| 接口 | 说明 |
|---|---|
| `search/type` | 需先访问首页拿 `buvid3`；返回数值型 play/like/favorites/danmaku/video_review；支持 `order`/`pubtime_begin_s`/`pubtime_end_s`/`tids`/`duration` |
| `ranking/v2?rid=` | 每分区 100 条，stat 完整（249/250/251 返回 -400） |
| `view?bvid=` | 完整 stat + cid + tname + owner |
| `tag/archive/tags`、`view/detail` | 标签 |
| `x/v2/dm/web/seg.so` | 弹幕，未压缩 protobuf，content 在 **field 7** |
| `x/v2/reply/wbi/main` | 评论，wbi 签名 + 游标翻页，每页 20 条 |
| `x/player/playurl` | durl 模式（`fnval=1`）最高给到 **720P**（实测 tkhd 1280x720） |

**已失效**：`comment.bilibili.com/<cid>.xml`（0 条）、`x/web-interface/newlist`（空）、
`x/web-interface/dynamic/region`（-404）。

**wbi 签名**：`nav` 匿名可取 `wbi_img`（img_key + sub_key），按固定打乱表取 32 位 mixin key，
参数排序后 `md5(query + mixin_key)` 作 `w_rid`。仓库里另有一份实现可对照：
MaiBot 主仓库里的 `plugins/github_airlibrax_game-update-watcher/core/adapters/bili_dynamic.py`。

## 四、两个致命坑

1. **`buvid3` 会把评论接口打残**：带 `buvid3` 请求评论 → 每页 3 条且 `is_end=True`；
   不带任何 cookie → 每页 20 条、可游标翻页。曾据此误判「评论必须登录」。
   伪造 SESSDATA 与裸请求结果完全一致，所以**本插件不需要 SESSDATA**。
   实现上必须开两个 client：搜索带 cookie，评论裸请求。
2. **视频 CDN 校验 Referer**：必须 `https://www.bilibili.com/`，否则 403。

## 五、风控与限流

- 评论接口 6 连发（间隔 1.5s）全部 `code=0`；搜索 5 连发正常。
- 插件内做了 1.2s 全局请求间隔 + 每轮最多 `max_check_per_run` 条候选，
  一次 run 的请求量约为「4 次搜索 + 8×(1 详情 + 3 评论) + 1~2 次下载」，量级安全。

## 六、投递链路的两个约束

1. 视频段必须是 `{"type": "video", "file": "<本地路径>"}` 这种顶层键写法；
   写成 `{"type": "video", "data": {...}}` 时宿主会剥掉 `type`，适配器认不出。
2. 插件↔宿主 RPC 帧上限 **16MB**，base64 会膨胀 4/3 → 大文件必炸，所以一律用路径引用。

## 七、投稿命中率实测（决定关键词池与检查上限）

候选池 = 5万~30万播放 + 评论 ≥40 条 + 时长 ≤240s。

| 关键词池 | 候选 | 通过「艾特率 ≥50% 且评论 ≥30」|
|---|---|---|
| 偏主流搞笑（整活/抽象/沙雕/搞笑/离谱/逆天/名场面/迷惑行为） | 15（两轮） | **0 条**（最高 32%）|
| 泛鬼畜混合（鬼畜/抽象/整活/绷不住/答辩/逆天/难绷/离谱…） | 10~12 | **2 条**（58.3%、53.3%；另有一条 78%）|

翻页深度不是关键变量：取 3 页 / 4 页 / 5 页 / 6 页，通过数都是 2/10。
但个别视频会随深度上升（有个样本 1 页 0% → 6 页 56%），所以 3 页是性价比最好的档位。

结论：`max_check_per_run = 12` 时，一轮大约能挑出 2 条通过判据的候选；
候选排序按 `min(video_review, 300)` 降序（封顶是为了不让长合集靠评论数霸榜）。

## 九、37MB 视频导致的三路投递失败（1.0.5 的病根；1.0.7 起只剩合并转发一种方式）

真机现象：插件报「投递失败」，紧接着群里却出现了一条视频和一个文件。

日志证据（本地时间 2026-10-11 14:19~14:20）：

```
14:19:50 [SendService] Platform IO 发送失败: platform=qq
         driver=gateway:maibot-team.napcat-adapter:napcat_gateway status=FAILED error=
14:20:05 ... 同上（直接发视频那次）
14:20:20 ... 同上（按文件发那次）
```

三点结论：

1. 三次都真的被判失败，`error` 是**空**的（NapCat 没给出原因），数据库里也没有成功记录；
   但「上传其实落到了群里、回执却是 FAILED」是可能发生的，所以群里的视频/文件不能当成功证据。
2. 根本原因是**体积**：那条视频 190 秒、720P 下 **35.4MB**，超过了 NapCat/QQ 可靠上传的范围。
   旧默认上限 40MB 允许了它。
3. 顺带确认：NapCat 适配器本身是健康的（`心跳 self_id=… online=True`），
   同期只有一个没起服务的 SnowLuma 适配器在反复重连，与本次失败无关。

修法见 1.0.5：上限收到 15MB + 下载前用 `size` 预判 + 超限自动降档 + 投递顺序按体积排。

## 十、命中率分析与三处偏差（1.0.8）

真机现象：连续 4 轮、36 条候选，全部卡在艾特率，一条没搬出来。
先看数据：**40 次"艾特率不够"的分布是 中位 8%、均值 11%、最高 37%**——不是差一点点，
而是候选本身就不行。

把当天所有采样合起来（约 70 条候选）：≥50% 的只有 6~7 条，**基础命中率约一成**。
但实际表现比这还差，原因有三处系统性偏差：

1. **排序挑错人**：原实现按 `min(video_review, 300)` 降序挑候选（想法是"分母要够"），
   而实测艾特率与评论数**反相关**——40~150 条评论中位 33%、150~300 条 21%、
   300~600 条 23%、600+ 条只 10%。等于每轮把最不可能过的先挑出来看。
   改为随机顺序，并加 `max_video_review`（默认 600）筛掉大热门。
2. **关键词池被稀释**：A/B 实测泛鬼畜词（鬼畜/抽象/整活/答辩/难绷/绷不住）中位 12%、最高 47%；
   泛搞笑词（沙雕/搞笑/名场面/迷惑行为/吐槽/社死/破防/离谱）中位 9%、最高 32%。
   默认池改为以前者为主。**注意这是关键词不是分区过滤**——分区限定确实更高
   （`tids=119 鬼畜分区` 采到 52%~66%），但用户明确要求不按分区。
3. **候选池被历史检查记录吃光**：搜索对同一关键词/排序/页码会把同一批视频反复捞出来，
   `_CHECKED_KEEP_DAYS = 60` 意味着被否掉的候选两个月内不再看，池子会逐步枯竭。
   改为 14 天（已搬过的仍永久记住）。

## 十一、点播后不回话：用钩子而不是提示词（1.0.7）

模型在调完工具后经常顺口说一句「搬着呢」「刚给你下了几个」，而需求是**群里只出现视频**。
提示词约束不住，所以改用机制：

- 触发工具时按 `session_id` 记一个「吞回话」窗口（`[tool].suppress_reply_window_seconds`）；
- 注册 `maisaka.reply.before_post_process` 钩子（BLOCKING + `ErrorPolicy.SKIP`），
  窗口内把 `kwargs["response"]` 置空 → 宿主判定「Hook 返回了空回复」→ **这次回复不发送**
  （见 `src/maisaka/builtin_tool/reply.py:494`）。
- 只吞点播后的**第一条**，随后正常聊天不受影响；开关是 `[tool].suppress_reply`。

## 十二、口语触发必须走命令链，不能只靠 LLM 工具（1.1.1）

真机现象：群里连问三次「来点好康的 / 来点涩的 / 来点好看的」，机器人只是**聊天式回绝**
（「好看的没有了」「再问就把我冻成冰雕送过去啦」），一次工具都没调用，插件日志里也没有
任何搬运轮次。**结论：把"点播"这件事完全交给模型决定，它就敢不调。**

改法：注册口语触发命令，用宿主已有的命令链（`re.compile(pattern).search(text)`，非锚定匹配）：

| 要点 | 说明 |
|---|---|
| 确定性 | 正则命中即执行，与模型是否配合无关 |
| 不回话 | 命令返回 `intercept_message_level=1` → 消息不进 LLM；命令的返回文字宿主只写日志、不发群 |
| 能拿到真实 QQ | 命令 args 里有 `user_id`（工具回调里该字段恒为空），白名单校验按真实 QQ 判 |
| 触发词 | `(?:来点\|来几个\|整点\|搞点\|发点\|给点\|找点\|搬点\|搬个…)` + 目标词（史/屎/抽象 ‖ 涩/色/黄/好看/好康/二次元/纸片人/mmd） |

21 条说法实测全对，且「这个视频真好看」「来点颜色看看」「色即是空」「搬砖去了」不会误伤
（触发词与目标词必须同时出现，且 `色` 前面用 `(?<!颜)` 排掉「颜色」）。

## 十三、好看频道为什么还要挡「教程」（1.1.2）

实测搬回来一条「【思路分享】怎么去丰富手书」：分区 同人·手书（在白名单里）、收藏率 23.6%
（远超 0.05 阈值）、时长 102s（在 120s 内）——**现有三条判据全都合格，但它是个教程**。

所以判据里补第四层：`[pretty].block_words`（标题/标签命中即跳过）。
分区白名单只能保证"是二次元"，收藏率只能保证"大家愿意收藏"，两者都不区分
「好看的画面」和「教你画画的讲解」——后者收藏率天然很高（干货类 fav/play 高是共性）。
默认挡：教程/教学/教你/手把手/零基础/入门/画法/步骤/解析/讲解/思路分享/干货/保姆级。

顺带修：好看频道的搬运记录原先存的是 `at_ratio`（恒为 0），`/搬史状态` 里显示成
「艾特率 0%」容易误会；现在记录里存 `channel` 与 `favorite_play`，状态命令按频道显示对应指标。

## 十四、收藏率的分母必须是「点赞」（1.1.3）

用户看到「收藏率 23.6%」觉得太低，要求至少 50%。查下来是**分母选错了**，不是阈值问题：

| 口径 | 中位 | 90% 分位 | 最高 | ≥50% 的候选（73 条） |
|---|---|---|---|---|
| 收藏/**播放** | 0.036 | 0.130 | **0.401** | **0 条** |
| 收藏/**点赞** | 0.516 | 1.606 | 3.060 | **39 条** |

收藏/播放到 50% 等于"每两个播放就有一个收藏"，B站上不存在（采样最高 40.1%），
把阈值设成 0.5 会让这个频道一条都搬不出来。而收藏/点赞中位就有 51.6%，
"收藏比点赞还多"（≥100%）的有 13 条，正是"值得反复看"的典型信号。

所以：`favorite_rate_metric = "fav_like"`（默认）+ `min_favorite_rate = 0.5`，
两个键都可配（想更严就 0.8/1.0）。转发文案与状态记录都标出口径，避免再被 23.6% 这种数字误导。

## 十五、「低创」用数值抓不住，只能语义判（1.1.4）

用户反馈搬回来「修着玩的新番 04」（UP：只是一个热心市民罢了，简介一行）——低创自制动画剧集。
把它和几条画面向内容放在一起对比：

| 视频 | 播放 | 点赞率 | 收藏/点赞 | 评论 |
|---|---|---|---|---|
| 修着玩的新番 04（垃圾） | 36478 | 3.8% | 1.89 | 158 |
| 开幕皮鼓（MMD） | 14428 | 9.6% | 2.09 | 15 |
| 黑丝党白丝党（壁纸） | 18568 | 1.8% | 1.78 | 9 |
| 安塞腰鼓（MAD） | 14810 | 1.9% | 1.80 | 6 |
| 这谁顶得住啊 | 138844 | 2.3% | 1.81 | 79 |

**没有任何一个数值能把「垃圾」和其他几条分开**——点赞率它 3.8%（比壁纸/MAD 还高）、
收藏率它也高、评论数它最多。所以只能按语义判，做了两层：

1. **规则层**：`block_words` 加低创剧集词（新番/自制剧/连续剧/小剧场/剧情向/大电影/剧场版/解说/配音）
   + 剧集编号正则 `_SERIES_RE`（`第\s*\d+\s*[集话期季]|EP\s*\d+|第[一二三四五六七八九十]+[集话期]`）。
   这条样本命中「新番」被挡下。
2. **LLM 复核层**：`ctx.llm.generate` 把标题/UP/分区/标签/数据给模型，问「是好看的画面向内容
   （MMD/插画/壁纸/手书/MAD/作画欣赏）还是低创剧集/剧情向/杂谈解说」，答「不要」换下一条。

**踩到的坑**：给桩写测试时用「prompt 里含『教程』」当判据，结果模板正文本身就有「教程讲解」
这个反面例子，导致好样本全被判不要——**写这类复核的测试要看结构化字段（标题行），不能拿整段
prompt 当判据**。实测规则层挡下两条垃圾样本，LLM 层在第一名被否时正确顺延到第二条。

## 十六、口径确认：要三类、不要五类（1.1.5）

用户看过几条后确认口味（原话是"不是很好"，追问他选了）：

| 要 | 不要 |
|---|---|
| MMD/3D 纸片人舞蹈 | 低创自制动画 |
| 动漫剪辑 MAD/AMV | 剧情/配音向短片 |
| 手书/同人动画 | （原有）教程/讲解 |
| | （隐含）静态图文/壁纸合集 |
| **虚拟主播不算问题**（Hololive 的 MMD 可以） | 但直播切片/会限/杂谈不要 |

据此改了三处：关键词池换成这三类的词、子分区白名单去掉 插画·绘画、LLM 判据重写。

**一个真实观察**：上一版 LLM 复核在真机上的判定不太稳——它一边说「不要，标签含虚拟偶像」，
一边又放行了一条 Hololive 的 MMD；还有一轮连续否掉三条（含 13.9 万播放的「这谁顶得住啊」）
最后本轮空手。所以提示词里必须把"虚拟主播本体不算问题"这种边界写清楚，
否则模型会凭直觉扩大打击面。

## 十七、后端读不到本地文件：视频改成内联 base64（1.2.2）

真机报错（经 SnowLuma 发私聊）：

```
对端动作返回失败: action=send_private_forward_msg
message=EACCES: permission denied, realpath '/root/maibot/MaiBot/temp/plugins/.../clips/BV1MVpX69EBL_64.mp4'
```

路径前缀 `/root/maibot/MaiBot/...` 说明 **SnowLuma 后端跑在另一个文件系统上**（Linux/容器），
它拿到的"本机路径"在那边并不存在或不可读 → 权限错误。NapCat 是同机所以一直没问题。

修法：转发里的视频段改成 `{"type": "video", "binary_data_base64": ...}`——数据随消息走，
与后端在哪台机器无关。约束是**插件↔宿主 RPC 帧 16MB**（base64 膨胀 4/3），
所以 `max_size_mb` 收到 10MB、`inline_video_max_mb` 也是 10MB，实测 6.3MB 文件载荷 6.3MB。
超过预算的才退回路径引用并打 warning（那种情况在跨文件系统后端上必失败，得让用户知道）。

**经验**：判断"投递失败"要看**错误来自哪一侧**——`适配器编码失败` 是本地问题，
`对端动作返回失败` 是后端/平台问题；两者修的地方完全不同。

## 十八、转发里 video 必须独占节点（1.2.1）

真机报错（经 SnowLuma 适配器发私聊）：

```
[SendService] Platform IO 发送失败: driver=gateway:...snowluma-adapter:snowluma_gateway
  status=FAILED error=对端动作返回失败: action=send_private_forward_msg
  message=message element "video" must be the only segment in a message
```

「文字 + 视频」放同一个转发节点会被**对端 QQ** 拒掉（适配器本身编码正常，
错误来自对端动作返回值）。改成两条节点——第一条只有说明文字、第二条只有视频后，
NapCat 与 SnowLuma 的编码结果都是 `{"type": "video", "data": {"file": "file://..."}}`
且 video 独占节点。**注意 NapCat 侧对同节点是容忍的**（早期就是那么发成功的），
但兼容两边就得拆开。

## 十九、"手动能发、定时发不出去"：过期聊天流（1.2.0）

真机现象：定时轮的日志写着「本轮已搬」，群里却什么都没有。

日志对出来的两个事实：

```
17:50:47 发送到 c1223fac...、c045968b...、83027b25...、4d5c3167...   ← 都是 2026-09-19 的老会话
         Platform IO 发送失败: driver=legacy.send.qq status=FAILED error=旧链发送失败
17:43:45 手动那次成功: drivers: gateway:maibot-team.napcat-adapter:napcat_gateway
```

查 `chat_sessions` 表：**四个目标每个都有两条会话**——一条今天活跃、一条 9 月 19 日。
宿主的 `_cap_chat_get_stream_by_group_id` 是

```python
stream = next((item for item in self._list_sessions(...) if str(item.group_id) == str(group_id)), None)
```

**取第一个匹配**，于是拿到过期那条；它的路由元数据是老的 → legacy 旧链 → 发送失败。
手动发送用的是消息自带的 `session_id`（活动流），所以一直正常。

**修法**（插件侧，不改宿主）：三层解析
1. 入站消息学到的「群/人 → 活动聊天流」，落盘持久化（我的 `chat.receive.after_process` 钩子本来就在收消息）；
2. 缓存为空时枚举同目标的多条会话，用 `message.get_recent` 挑"最近有消息"的那条；
3. 都拿不到才回退宿主查询。

**同时修掉一个误报**：投递失败时 `Deliverer` 仍返回 `method="forward"`，
而调用方用 `bool(result.get("sent") or result.get("method") == "forward")` 判成功——
四个目标全失败也会记成「本轮已搬」并写进已搬记录，让记录里混入假条目。现在只看 `sent`。

**教训**：只要发送链路上有"失败也返回某个字段"的情况，用那个字段做 `or` 判断就会伪造成功；
判定成功只认一个权威字段。

## 二十、没找到就继续找（1.1.8）

原本一轮没挑到候选就直接返回"本轮没有通过判据的候选"，用户要求"没找到继续找"。
实现：`Pipeline.run_once` 里把挑候选包成循环，最多 `[retry].rounds` 轮（默认 3），
轮间 `gap_seconds`（默认 15 秒）。每轮都重新随机关键词/翻页，所以候选池会换一批；
好看的 picker 会把规则否掉的候选标记已检查，因此重试会自然往下走而不会原地打转。

**代价要清楚**：搬史一轮最多 8 次搜索 + 16 次"1 详情 + 3 页评论"（约 70 个请求），
三轮就是 ~200 个请求；好看一轮约 6 次搜索、很便宜。所以要吵就把 rounds 调小。

## 二十一、点播不限次数，只留最小间隔（1.1.7）

用户要求：去掉指令与工具路径的冷却和每日次数，但"间隔过少可以拒绝"。所以：
删掉 `cooldown_minutes`（10 分钟）与 `daily_limit_per_group`（每群每天 3 次），
换成 `min_gap_seconds`（默认 60 秒，0 = 不挡）——只拦"刚搬完又来一条"的贴脸请求。
两个频道的间隔分开记（记账键 `stream` / `stream#pretty`）。

同时保留原有的两个守卫：并发忙锁（`_manual_busy` / `_running`，防止同时跑两轮）与
`[tool].permission` 权限（anyone/whitelist）。工具是否被调用仍由模型自己决定。

## 二十二、LLM 复核被去掉了（1.1.6）

1.1.4 加过一层 LLM 语义复核，1.1.6 按用户要求完全删掉，原因有两条：

1. **真机判定不稳**：同一轮里一边以「标签含虚拟偶像」为由否掉候选，一边又放行了一条
   Hololive 的 MMD；还有一轮连否三条（含 13.9 万播放的动画剪辑）后本轮空手。
2. **可预测性**：频道行为不该随模型口味变。现在只看规则——关键词池、子分区白名单、
   屏蔽词（教程/讲解 + 低创剧集 + 直播切片）、剧集编号正则、时长与收藏率阈值。
   要收紧/放宽就是改一个列表，不需要验证模型判得对不对。

顺带记一条经验：**用 LLM 做内容判定时，提示词里的"反面例子"会污染判定**——
给桩写测试时我拿「prompt 里是否含『教程』」当判据，结果模板正文本身就有"教程讲解"，
导致好样本全被判不要。测试必须只看结构化字段。

## 二十三、「来点好看的」频道的数据依据（1.1.0）

需求：时长不长、收藏率高、**只要二次元不要真人**。

**采样（170 条原始候选，10 个关键词 × 2 个排序，page=1）**

过滤链：时长 ≤120s 砍掉 53 条、子分区不在白名单砍掉 44 条、疑似真人词表砍掉 0 条 →
剩 73 条。**真人向内容是被子分区白名单挡掉的**，词表只是兜底。

**为什么用「收藏/播放」而不是「收藏/点赞」**

| 口径 | 分位数 |
|---|---|
| 收藏/播放 | 中位 0.039、70% 位 0.071、80% 位 0.097、90% 位 0.130、95% 位 0.191、最高 0.402 |
| 收藏/点赞 | 二次元内容上大量落在 0.3~2.1，混作一团没有界线 |

所以阈值取 `min_favorite_play = 0.05`（约留四成）：阈值 0.03 留 45 条、0.05 留 30 条、
0.08 留 18 条、0.12 留 9 条。

**二次元 vs 真人的判别靠子分区（typename）**

搜索接口返回的 `typename` 是**子分区**，实测分得很干净：

| 二次元向 | 真人向 |
|---|---|
| MMD·3D、同人·手书、MAD·AMV、人力VOCALOID、绘画、动画综合 | 仿妆cos、颜值·网红舞、舞蹈综合、特摄 |

所以白名单默认包含 MMD/手书/MAD/AMV/VOCALOID/动画/同人/插画/绘画/动漫/虚拟。
注意 `宅舞` 是真人出镜（虽属二次元文化），默认**不在**白名单里，需要的话自己加。

**一个踩到的坑**：搜索结果里**没有 cid**，而取播放地址必须要它——
第一版直接拿搜索结果造 Candidate，`playurl` 报 `code=-400 请求错误`。
现在选中后会拉一次 `video_detail` 补齐 cid/aid，并用详情里的真实数据复核时长与收藏率，
拿不到就顺延下一条。

## 二十四、自然语言点播的身份校验怎么做

Tool 回调里**拿不到点播者的真实 QQ 号**（群聊场景下工具回调的 `user_id` 恒为空，
这是宿主的既有行为）。但身份不是没法判——**入站钩子带真实发言者**，所以做法是：

1. 注册 `chat.receive.after_process`（`HookMode.BLOCKING` + `ErrorPolicy.SKIP`，只读不改写），
   把「会话 → 最近一位真人发言者」连同时间戳缓存起来（有 TTL，条目有上限）；
2. 工具触发时按 `stream_id` 回查，再跟 `[tool].whitelist` 比对。

两个必须知道的取舍：

- 缓存的是「该会话最近发言者」，不是「本次调用的发起者」。同一群多人抢话时会错位，
  所以白名单模式下**认不出发言者一律拒绝**（宁可少搬也不放过），而不是默认放行。
- 默认仍是 `permission = "anyone"`（群里谁都能点播），因为这是插件的使用场景本身；
  想收紧就改 `whitelist`。最严格是 `[tool].enabled = false`，只留管理员命令。
