# P2：点歌音频下载未校验导致语音发送失败

## 现象

点歌命令能够完成搜索和下载，并生成临时音频文件，但发送到虚拟麦克风时出现 MPEG 头解析失败。日志随后显示临时文件不存在，容易误判为文件提前被删除。

## 根因

下载层只确认 HTTP 响应内容能够写入文件，没有确认响应内容是可被发送链路使用的音频。音源服务返回 HTML、JSON 错误页、空内容或不兼容音频时，错误会延迟到虚拟麦克风的解码阶段才暴露。

语音发送服务只会在发送流程结束后清理临时文件，因此“文件不存在”是底层解码错误的泛化提示，不是本次问题的首要原因。

## 方案选型

### 方案一：只检查 HTTP 状态码

优点是实现简单、开销低。

缺点是很多错误页面仍可能返回 200，无法识别内容类型错误；不能解决音频编码不兼容。

### 方案二：下载后使用同一音频解码器校验

下载完成后使用虚拟麦克风实际使用的解码库检查采样帧、采样率和声道信息；校验失败时删除临时文件并让上层继续尝试下一个音源。

优点是校验结果与最终发送链路一致，能在降级窗口内发现问题。

缺点是下载后会增加一次文件头解析，并受本机音频库格式支持范围影响。

### 方案三：引入 ffprobe 或统一转码

优点是格式兼容性和诊断能力更强。

缺点是增加外部程序依赖、部署复杂度和转码延迟；当前项目暂不需要。

## 当前方案与妥协

采用方案二，同时记录音源标识、脱敏后的 URL、HTTP 状态、响应类型、响应长度、下载字节数、解码信息、耗时和失败原因。日志不记录查询参数值或请求头值，避免泄露签名和密钥。

暂不引入转码工具；如果后续确认某个正常音源只返回当前解码库不支持的编码，再单独评估转码依赖。

## 教训

1. “文件写入成功”不能等同于“媒体资源有效”。
2. 多阶段链路应在组件边界验证数据，而不是等最终设备层报错。
3. 降级逻辑必须覆盖解析失败、下载失败和媒体校验失败。
4. 清理日志应结合时间顺序判断，不能仅凭底层库的通用错误文本定位根因。
