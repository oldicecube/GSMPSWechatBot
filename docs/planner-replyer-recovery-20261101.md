# Planner missing-action recovery and Replyer message boundaries

Date: 2026-11-01 (Asia/Shanghai).

## Observed failure

Recent QQ and WeChat Planner logs from 16:36–16:43 show final decisions such as
“调用 reply 进行回复” and “不需要调用其他工具，直接回复即可”, with **no function call**.
In native normal mode, text alone ends the thinking cycle. Only passive mode
interprets text as reply guidance. The user therefore saw a reply decision in
WebUI but no delivered answer. This was not a Replyer send failure.

## Bounded normal-mode extension

- Explicit action decisions without actual function calls trigger one protocol
  correction request, using the real currently available tools.
- Corrected function calls follow the existing tool registry execution path.
- If correction still explicitly decides to reply without a function call, reuse
  the native text-guidance entry once, with the frozen real target message.
  `execute_reply` and Replyer still generate and send the final text.
- Explicit silence remains silence. Pending queries are not replaced by made-up
  results or by a reply claiming they succeeded.
- No retry occurs after a reply generation or delivery failure; partial receipts
  remain recorded. Planner prose is never sent directly as visible speech.
- Passive mode keeps its existing protocol. This correction is an adapter
  compatibility extension around normal-mode model output, not an upstream
  version upgrade or a new direct-send path.

## Independent messages generated by Replyer

The old shell core returned an ordered `messages` array. The same useful property
is retained without imposing its JSON schema on the native Replyer:

- A small layout instruction lets Replyer use blank lines between independent
  conversational messages when appropriate. It can still answer in one message.
- The native post-processing stage preserves these chosen boundaries instead of
  randomly merging them or splitting complete short sentences by punctuation.
- Fenced code, lists, headings, quoted blocks and tables stay intact. Overflow
  joins the tail rather than dropping content or sending an unbounded burst.
- Existing `response_splitter.enable` and `max_split_num` settings control the
  feature. Current deployment allows up to three messages. No new persona,
  expression, catchphrase or topic instructions are introduced.
- Every fragment follows the normal current-stream send path, in order, with its
  own external receipt and history record. Mentions are attached to the first
  fragment and the selected emoji is attached once afterward.
