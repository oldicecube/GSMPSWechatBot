# 双端搬屎与玩家监控投递修复

## 行为与原因

- 搬屎来源通过 SDK 的 `tool.get_definitions` 查询 Host 注册表，兼容 SDK 返回的列表及原始信封；Runner 不再导入独立的 Host 单例。每轮刷新，兼容贴吧稍晚加载。
- 来源优先级为贴吧、B 站、QQ 收藏包。已发送即停止；只有确认未发送才继续下一来源。RPC 超时为未知结果，不继续补发。
- 每个目标群独立调度、加锁和记录搬屎限额。空的近期消息窗口允许产生机会；不要求先有人发链接。普通自主生活的每日分享限额保持原义，搬屎不再消耗这部分额度，也不被其他群的冷却和生活任务退避吞掉。
- 一次性授权按随机令牌保存，避免双端覆盖。发送前持久化预约，重载时预约转为未知状态，已消耗限额不会被重置。
- 长请求显式设置 SDK 外层 RPC 超时，覆盖原先默认 30 秒的过早超时。
- B 站在 QQ 使用原生合并转发、真实适配器账号和本地视频路径；微信保持说明文字与 MP4 文件。未知会话来源拒绝发送。
- 贴吧公开 API 等待实际搬运结果，区别于原来只返回“已开始”的后台工具。QQ 使用合并转发，微信使用原生图片文件投递。长图发送失败不再被算成送达；合并转发节点使用目标适配器账号。
- QQ 收藏包来源使用已保存且允许转发的群聊记录包，跳过私聊包和当前群自身的包，不再把当前群最后几条消息包装后发回原群。
- `player_monitor` 在广播时补充原生已允许的 QQ 群，携带账号、连接、平台及群号；仍检查群开关与插件权限。单个目标失败不会阻止后续目标，逐群记录真实发送结果。

## 文件

- `core/dispatcher.py`：玩家监控广播目标及回执。
- `utils/plugin_stream.py`：通过 SDK 查询真实群聊会话来源。
- `plugins/mai-repost-shit/plugin.py`、`core/sources.py`、`core/activity.py`、`core/deliver.py`、`core/pipeline.py`、`_manifest.json`：来源、调度、长 RPC、双端媒体路由。
- `plugins/autonomous_life/plugin.py`、`store.py`：按群搬屎额度、授权、持久化及独立调度。
- `plugins/tieba_share/plugin.py`、`_manifest.json`：同步 API、双端长图发送和准确回执。
- `plugins/cateye_mai_forward/plugin.py`：已授权收藏包 API、发送结果及 SDK 列表兼容。
- `scripts/repost_dual_delivery_acceptance.py`：双端隔离验收。
- `scripts/maibot_autonomous_life_acceptance.py`、`scripts/maibot_repost_planner_acceptance.py`：适配新的 SDK 调用与独立搬屎额度；单端历史夹具不再假装有第二个会话。

本地搬屎配置的来源列表已调整为贴吧优先；本地配置、令牌和运行数据不提交。

## 当前运行限制

诊断时 QQ WebUI 的实时状态为 `waiting_qrcode`，未登录；OneBot 配置与适配器均使用本机 13001，端口没有监听。3001 属于 WeFlow，不能改作 QQ 端口。旧登录状态文件曾显示在线，但它是旧快照；本次已更新为实时离线结果，并打开本机登录页面。

QQ 登录恢复前无法验收真实 QQ 投递。插件被现有文件监控器自动热重载；未手动重启主 bot 进程。壳子 `Dispatcher` 的监控广播修复需要用户手动重启主进程后生效。生产自动调度器可能自行运行，不能把隔离测试结果或排队成功当作实际群送达。
